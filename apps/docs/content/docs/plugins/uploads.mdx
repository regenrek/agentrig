# Submission contract

Use AgentRig to submit one pinned upstream snapshot for review:

```bash
agentrig login
agentrig plugin submit owner/repo@v1.2.3
```

`agentrig plugin submit` creates a review submission from one resolved source.
The source can be a tagged local checkout, a GitHub shorthand, or a GitHub repo
URL plus a version tag:

```bash
agentrig plugin submit . --version v1.2.3
agentrig plugin submit owner/repo@v1.2.3
agentrig plugin submit https://github.com/owner/repo --version v1.2.3
```

If the plugin lives below the repo root, pass its repo-relative path:

```bash
agentrig plugin submit owner/repo@v1.2.3 --path plugin
```

Skill, MCP, and hook submissions use the same source shape:

```bash
agentrig skill submit owner/repo@v1.2.3 --path skills/review
agentrig mcp submit owner/repo@v1.2.3 --path mcps/github
agentrig hook submit owner/repo@v1.2.3 --path hooks/pre-submit
```

To check review progress later:

```bash
agentrig plugin status
```

You can also pass a submission id directly:

```bash
agentrig plugin status <submission-id>
```

The web submission UI at `/submit` uses the same resolved provenance model.

## What happens after submission

The normal path looks like this:

1. submit one exact upstream snapshot
2. AgentRig validates and scans it
3. an admin reviews it in the web app
4. approval opens or updates a PR into `agentrig-registry`
5. the version becomes publicly installable only after that PR is merged

## Important boundary

Submission is **not** a public install source.

A submission can support:

- review
- validation
- promotion into a canonical registry workflow

It does **not** make author repos, ZIPs, arbitrary URLs, or Convex-hosted payloads installable.

## Source rules

AgentRig resolves every source to one pinned repo, tag, commit, and repo-relative
plugin path.

Rules:

- GitHub sources must resolve through a real Git tag.
- Branch names, raw commit SHAs, `latest`, floating refs, ZIP uploads, and
  alternate GitHub URL shapes are not valid submission inputs.
- `--path` is always relative to the source repo root. `.` is valid for a root
  plugin.

## Validation boundary

Submission validates at least:

- repo reachability and normalization
- tag-to-SHA consistency
- exact plugin root existence
- `.plugin/plugin.json` presence and validity
- manifest version consistency with the submitted tag
- path safety, symlink/submodule rejection, and forbidden file types
- install surface and scan results needed for later registry artifacts

## Submission statuses

The submission pipeline uses these statuses:

- `pending_validation`
- `validating`
- `pending_review`
- `accepted_for_pr`
- `rejected`
- `blocked`

Validation scan status is tracked separately as `pass`, `warn`, or `fail`.

## Security notes

- Never submit sources that contain secrets.
- Review and validation reduce risk, but install trust still belongs to signed registry state, not to submission itself.
